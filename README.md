# 尼康优化校准（.NCP / .NP2 / .NP3）格式分析与转换工具

English version: [README_EN.md](README_EN.md)

对尼康优化校准（Picture Control）文件格式的逆向分析，以及把新版 `.NP2` / `.NP3`
预设降级转换为 `.NCP` 的工具——`.NCP` 是老机身（尼康 D300 / D300S / D90 等）
唯一能识别的格式。

文中所有数字都来自对真实文件的实测，不是推测。

> **看结果**：30 支最新版 NCP 与「最新优化校准」原版的逐支对比图和完整数据表 →  
> [在线报告（30 张三联图 + 明细表）](https://pinksert.github.io/Nikon-Picture-Control-NCP-Analysis/d300/charts/v3-gap.html)  
> （见第十二节）
样本：用尼康 Picture Control Utility 2 导出的 42 个原厂预设
（6 个 .NCP、8 个 .NP2、28 个 .NP3）。

## 一、三代格式

| | NCP | NP2 | NP3 |
|---|---|---|---|
| 版本串 | `0100` | `0210` | `0300` |
| 容器 | 抬头 + 类型/长度记录 | TLV 卡片链 | TLV 卡片链 |
| 大小 | 恒 52 字节（不带曲线） | 208 + 8 + 说明文字 | 248 + 8 + 说明文字 |
| 机型 | 所有支持优化校准的老机身 | D810 起 | Z 系列、D6、D780 |
| 新增参数 | — | 清晰度 | 快速锐化、中等锐化、效果级别 |

三代文件的魔数相同：`NCP\0`。

## 二、NCP（0100）布局

```
偏移 0    4   "NCP\0"
偏移 4    4   记录类型 = 1（配置数据）
偏移 8    4   记录长度 = 36
偏移 12   4   版本 "0100"
偏移 16   20  名字，ASCII，补零
偏移 36   2   底子（基准曲线）编号，大端
偏移 38   1   是否被用户修改
偏移 39   1   0xFF（用途未明）
偏移 40   8   八个滑块
偏移 48   4   0x00000000（结束标记）
合计 52 字节
```

滑块字节 = `数值 + 0x80`，范围 −126…126，另有三个哨兵值：

| 字节 | 含义 |
|---|---|
| `0x00` | 自动（−128） |
| `0x01` | 曲线接管（−127）——见于对比度/亮度，表示交给 LUT |
| `0xFF` | 不适用（127） |

滑块顺序：锐化、对比度、亮度、饱和度、色相、滤镜效果（单色）、调色（单色）、调色强度（单色）。

NCP 时代认得的底子编号只有六个：

```
0001 标准   03C2 中性   00C3 鲜艳
0486 人像   04C7 风景   064D 单色
```

`028E`（平面）、`02CF`（自动）和 20 个创意编号 `0801`–`0814` 在 NCP 里
**不存在**——文件照样能生成，但老机身没有对应的曲线。

单色调色枚举（与 D300 菜单顺序一致，已与公开逆向文档交叉验证）：
`0 黑白、1 棕褐、2 青、3 红、4 黄、5 绿、6 蓝绿、7 蓝、8 紫蓝、9 红紫`。
单色滤镜：`0 关、1 黄、2 橙、3 红、4 绿`。

## 三、NP2 / NP3（0210 / 0300）布局

魔数之后是 TLV 卡片链，每张卡 `type(4) + length(4) + data`，以 4 字节 0 结束。

```
type 0x100   版本串（"0210" / "0300"）
type 0x200   名字，UTF-16BE，20 字节
type 0x300   底子编号（2 字节）              ← 与 NCP 同一套编号
type 0x400   恒 00 00
type 0x500   恒 FF 01
type 0x600   锐化
type 0x700   清晰度                          ← NP2 起，NCP 无对应位
type 0x800   对比度
type 0x900   亮度
type 0xA00   饱和度
type 0xB00   色相
type 0xC00   滤镜效果（单色）
type 0xD00   调色（单色）
type 0xE00   调色强度（单色）
type 0xF00..0x1200   保留，FF 01
type 0x1300..0x1600  NP3 独有（快速锐化 / 中等锐化 / 效果级别等）
type 0x10100 说明文字
```

数值编码：`值 = (字节0 − 0x80) × 字节1 / 16`。步进码 `04` 表示 0.25 一档；
`0xFF` 表示不适用。

## 四、NP2 / NP3 → NCP 映射

```
卡 0x600 锐化      → NCP[40]
卡 0x800 对比度    → NCP[41]
卡 0x900 亮度      → NCP[42]
卡 0xA00 饱和度    → NCP[43]
卡 0xB00 色相      → NCP[44]
卡 0xC00 滤镜      → NCP[45]
卡 0xD00 调色      → NCP[46]
卡 0xE00 调色强度  → NCP[47]
卡 0x300 底子编号  → NCP[36:38]
```

实测：8 个滑块位 × 6 个预设 × 2 种新格式 = **96 字节，96 个全中**。
端到端：6 个预设 × NP2/NP3 = 12 个文件重建后与尼康原版 NCP
**逐字节一致（52/52）**。

### 转不动的部分

* **卡 0x700（清晰度）**——NCP 没有这个位置。
* **卡 0x1300–0x1600**——NP3 独有，NCP 无对应。
* **0.25 档**——NCP 是整档，比如中性在 NP3 里的 +0.50 只能记成 0 或 1。
* **量程**——NP2/NP3 亮度到 ±1.5（NCP 只有 ±1）；NP3 锐化到 −3（NCP 最小 0）。
* **底子曲线**——平面/自动/20 个创意编号在 NCP 里没有等价物。底子 TRC
  存在相机固件里，永远导不出来，NCP 只存编号。这才是创意预设无法
  真正移植的根本原因。

`np2ncp.py --approx` 会把认不出的底子替换成六个已知底子里最接近的
（平面→中性、自动→标准、黑白类→单色、其余→标准），让文件至少能被
加载——但这是近似，不是转换。

## 五、用户自定义曲线（UDC）

NCP 可以带一条用户曲线，即 type=2 的记录。以下结构通过逐字节重建
一份真实的 PCU2 导出文件得到确认：

```
"NCP\0"
type=1  len=36   配置数据
type=2  len=578  ├─ 0..63    头部
                 └─ 64..577  257 × uint16 大端，0..32767
type=0
合计 638 字节
```

* LUT 输入索引 `i`（0…256）对应输入 `i/256`。
* 输出是 15 位，满量程 32767，必须单调。
* UDC 作用在 **sRGB（1/2.4）伽马之后**，是成像流水线的最后一步——
  它是只管亮度的一维 LUT，表达不了色彩偏移。

### 头部

```
字节 0-7   49 30 00 FF 00 FF 01 00   所有 observed 文件相同
                                     （前两字节不是任何常见 CRC16）
字节 8     控制点个数
字节 9..   控制点，每点 2 字节：(x, y)，8 位，x 递增
```

真实文件读出的例子：

* 3 点 → `(0,0) (73,140) (255,255)`；该文件 LUT 在 x=73 处为 54.7%，
  而 140/255 = 54.9% ✓
* 4 点 → `(0,0) (69,175) (179,81) (255,255)`——升、降、升，正是
  编辑器里画出的那条非单调波浪 ✓

**重要**：尼康软件是按这些控制点重算曲线的。如果只换 LUT 不换控制点，
显示的曲线和实际生效的曲线都会跟你写的不一样。**两边必须写同一条曲线。**

尼康控制点之间的确切样条算法未确认。用 3 个控制点重建真实 LUT 的误差
（满量程 32767）：分段线性 2031、Catmull-Rom 1673、自然三次 9783、
单调三次 612。本工具不赌算法，而是**取满 20 个控制点**密集采样目标
LUT，误差降到 0.6–14.6——无论它用什么插值都可以忽略。

## 六、从照片反推预设的影调曲线

UDC 是流水线最后一步，所以"标准 → 目标预设"的曲线可以直接测量：

1. 同一张 NEF 在尼康工坊里导出两次，滑块全部默认：
   一次 STANDARD，一次目标预设。导出设置完全一致（sRGB、8 位、同尺寸）。
2. `make_curve_batch.py` 会从每张 JPG 的 MakerNote 里认出用的是哪个预设
   （搜 `03100310` 标记，名称在 +8、底子编号在 +48 小端），按亮度分箱
   统计，生成 257 点 LUT。
3. 写出 638 字节的 NCP，控制点与 LUT 同一条曲线。

实测（人像 vs 标准，12,212,224 像素）：

| | 套曲线前 | 套曲线后 | 目标 |
|---|---|---|---|
| 亮度均值 | 91.25 | 95.52 | 95.51 |
| 逐像素亮度差 | 7.73 | 2.56 | — |

色彩是另一回事——色度 a\* 2.21→1.93、饱和度 2.41→2.17，大约只兑现
**10%**。一维亮度 LUT 复现不了预设的色彩运算。**黑白类和调色类预设
是这套方法的主场；彩色创意预设只能做到影调像、味道不像。**

### ⚠️ 验证/预览必须用「与照相机兼容」

实测发现（尼康工坊）：同一个带曲线的 NCP，

* 在**「与照相机兼容」**下，每个字节语义正确：`01` 被理解为曲线接管，
  UDC 完整生效——这是文件设计时针对的管线，也是老机身机内的真实行为；
* 在**「最新的优化校准系统」**下，工坊把 NCP 的滑块按新参数表的**位置**
  硬套：对比度（`01`）显示成「中等锐化 1.00」、亮度（`01`）显示成
  「清晰度 1.00」。曲线哨兵在新面板里没有对应位置，被当成数值 +1。

所以新版系统下的预览只能当参考，**验收以「与照相机兼容」和实机为准**。

## 七、用法

```bash
# 原样降级（底子编号照抄，认不出的会标出来）
python np2ncp.py <含 .NP2/.NP3 的目录> [输出目录]

# 近似模式：把认不出的底子换成六个已知底子里最接近的
python np2ncp.py <目录> [输出目录] --approx

# 查看真实 .NCP（摊开每条记录和曲线 hex）
python np2ncp_curve.py dump <文件.ncp> [输出.txt]

# 用文件自身的字段重建一份，逐字节比对
python np2ncp_curve.py rebuild <文件.ncp>

# 从两张导出图反推曲线
python np2ncp_curve.py measure <标准版.jpg> <目标版.jpg> <lut.json>

# 批量：一个目录的导出图，以 STANDARD 为基准
python make_curve_batch.py <jpg目录> [输出目录]

# 曲线实际还原了多少
python verify_curve.py <标准版.jpg> <目标版.jpg> <lut.json>
```

## 八、已解决的问题

按发现顺序排列，每一条都有文件或图像上的实测依据。

1. **三代容器的结构差异**——魔数、版本串、TLV 卡片链、记录类型与长度，
   42 个原厂预设摊开比对得出。
2. **NP2/NP3 → NCP 的参数映射**——8 个滑块位 × 6 个预设 × 2 种格式
   **96 字节全中**；6 个预设重建后与尼康原版 **逐字节一致（52/52）**。
3. **底子编号体系**——NCP 只认六个；平面、自动和 20 个创意编号没有对应物，
   这是创意预设无法移植的根本原因（不是格式没破解，是曲线在固件里）。
4. **单色滤镜与调色枚举**——与公开逆向文档交叉验证一致。
5. **带曲线 NCP 的 638 字节结构**——64 字节头部 + 257×uint16 LUT，
   通过逐字节重建真实导出文件确认。
6. **头部控制点编码**——字节 8 是点数，字节 9 起每点 (x, y)；用两份
   不同曲线的导出文件对比确认。
7. **"改 LUT 不改控制点"导致的曲线错乱**——尼康软件读的是控制点，
   只换 LUT 会让显示和实际效果都不对。解法：控制点与 LUT 写同一条曲线，
   并取满 20 点让插值误差降到可忽略（0.6–14.6 / 32767）。
8. **曲线没有针对老机身**——最初用「新系统标准 → 新系统人像」测，
   但 NCP 在 D300 上跑的是老管线，LUT 叠在另一条底子上必然偏。
   解法：基准图改用「与照相机兼容 + STANDARD」导出。
9. **尼康的插值算法未知**——用带 tension 的 Catmull-Rom 拟合失败
   （两个样本最佳参数 1.20 / 0.98 不一致）。解法：不猜算法，改**黑盒闭环**——
   导出一张 → 算残差 → 修控制点。一轮即收敛：亮度残差 9.48 → **2.02**，
   未参与校准的另一张图残差 **2.01**（说明曲线泛化，不是过拟合）。
10. **饱和度与色相滑块的标定**——用 4 个标定 NCP（饱和度/色相各 ±1）导出后实测，
    在对称线性假设下由 ±1 的比值与差值解出（无需 0 点基准）：
    **饱和度每档 = 色度 ×1.267，色相每档 = 3.46°**。据此把 30 个预设的色彩需求
    折算成了档位（钳位在 ±3 档）。
11. **头部偏移 bug 的定位与修复**——修正滑块时把头部取成了 `b[64:128]`（正确是
    `b[56:120]`），控制点区被错位数据覆盖，工坊重算曲线后画面色块化。已用批量同款的
    `hdr_with_delta()` 重建头部修复，并记下教训：偏移一律走解析函数，不手写数字。

关于第 9 条，最终成品（人像）的实测：

| | 套曲线前 | v2 | v3 | 目标 |
|---|---|---|---|---|
| 亮度均值 | 89.46 | 86.12 | **95.53** | 95.51 |
| 逐像素亮度差 | 6.49 | 9.48 | **2.02** | — |

## 九、未解决与未验证

**未解决（格式层面）**

* 头部字节 `0..7` 的用途，尤其 `49 30`——不是 XMODEM/CCITT/MODBUS/Kermit
  任一种 CRC16，也不是简单和校验。
* 尼康控制点之间的确切样条算法（已放弃破解，改用黑盒迭代绕过）。
* `PINK` 的调色颜色——按 9（红紫）处理，未确认；SEPIA/BLUE/RED 已确认。
* NP3 卡 `0x1300`、`0x1400`、`0x1600` 的语义（步进码不是常规的 `04`，
  数值公式对它们不适用）。
* 20 条创意底子曲线本身：它们在固件里，任何文件格式层面的办法都
  带不到老机身上。

**未解决（原理性限制，绕不过去）**

* **选择性色彩运算无法还原**——这是最终定论，有实测支撑。把 DREAM 的残余差异
  按色相区域分解（见 `data/hue_breakdown.json`）：

  | 色相带 | 像素占比 | 色度差（目标−我们） | 色相偏移 |
  |---|---|---|---|
  | 红 | 7.1% | −10.53 | −1.5° |
  | 橙 | 9.8% | −9.98 | +1.0° |
  | 黄 | 33.7% | −0.18 | −0.1° |
  | 黄绿 | 31.1% | +3.28 | −4.0° |
  | 绿 | 7.2% | +10.90 | −15.7° |

  差异随色相带剧烈变化（−10.5 到 +10.9），黄色区几乎完美而红/绿两个方向相反——
  这是**选择性色彩运算（色彩矩阵）的指纹**。创意预设的精髓就在这里：
  把红色压下去、绿色提上来、绿色相偏移十几度。而 D300 能执行的工具全是**全局**的
  （饱和度管所有颜色、色相转所有颜色、曲线管所有亮度），数学上无法表达
  "只压红不动黄"。**这不是格式没破解，也不是校准不准——是 D300 的处理引擎
  没有这个能力，属于硬件/固件的代际差异。**
* **色彩倾向无法用一维 LUT 还原**（同上，本质相同）。
* **清晰度、快速锐化等新参数**在 NCP 里没有位置，只能丢。
* **测量模型的适用边界**：给彩色创意预设算"需要多少饱和度"时，用的是
  "只改亮度、保持色相"的简化模型，对 DREAM 这类强色偏预设会失效
  （实测出现滑块方向反常）。该测量只对低饱和/单色类可靠。

**未验证**

* ~~所有验证都是在尼康工坊软件里做的，尚未在 D300 实机上试过~~ —— **已在真机上跑通**
  （见第十一节与 `d300/`）。插卡 → 机内载入 → 实拍 → 像素级比对，三轮共 29 张实拍，
  机内确实是按同一套控制点/LUT 行为处理的，并且**固件也做了工坊那层曲线前变换 H**。
* 只有**人像、DREAM、SILENCE** 三个预设做过"导出 → 残差 → 修正"的闭环；
  其余 27 个只走了一遍测量，没有逐个验证。
* 校准只用了两张照片，虽然在未参与校准的图上验证了泛化，
  但极端场景（高反差、夜景、大面积单色）未测。

## 十、这套方法能搬到什么程度

| 能搬 | 搬不了 |
|---|---|
| 影调 / 亮度映射（残差可做到约 2/255） | 分色相区域的选择性色彩处理 |
| 整体饱和度与色相倾向（已标定档位） | 色彩矩阵级运算（引擎代际差异） |
| 单色化、单色调色（滤镜/调色枚举） | 清晰度、快速/中等锐化等新参数 |
| 底子载体（六个已知编号） | 创意底子曲线本身（在固件里） |

**结论**（下面这条已被 D300 实拍样片修正，以前只是推测）：

- **黑白类**（木炭、石墨、双色、黑碳、单色系）：能达到接近效果，实测平均差 3.5–5.8 级；
- **调色类**（棕褐、蓝、红、粉）：第一版平均差 13.1–16.4 级，是全部 30 支里最差的一组。
  原因不在校准，而在路线：这类预设是「低饱和、仍留部分色彩 + 轻调色」，
  若按「单色底子 + 浓调色」实现，就会把原版残留的彩色全部抹掉（实测彩度只剩原版的 26%–81%）。
  **第二版已按这个判断重做**：调色强度从 `0x84` 退到 `0x81–0x82`，四支平均 **14.4 → 8.2 级**，
  不再是短板（见 `d300/docs/08-tone-color-v2.md`）；
- **彩色创意**：只能做到"影调像、颜色不像"（实测影调偏差 ≤4 级，差距全在饱和度与色罩）。
  颜色差异是原理性的，不是校准不到位。

## 十一、实机落地篇（D300）

[d300/README.md](d300/README.md) 是把这套方法推到真机的记录，包含上游这份分析**需要更正的地方**：

- **卡上路径定案**：D300 固件里只有 `A:/NIKON/CUSTOMPC/PICCON%02d.NCP` 一条路径，没有根目录扫描
- **四处更正**：名字卡是 ASCII 20 字节（不是 UTF-16BE，`np2ncp.py` 因此写出 `????`）；说明卡是 UTF-8；单色调的调色枚举在文件里是「不适用」、无法从数据侧确认；LUT 不需要单调
- **底子编号：`0x0001` 标准 / `0x03C2` 中性 / `0x00C3` 鲜艳 / `0x064D` 单色，四个都是 D300 自己固件里
  写明的码**（在 `B3000111.bin` 里紧贴着 `STANDARD` / `NEUTRAL` / `VIVID` / `MONOCHROME` 四个名字）。
  此前把它们记成「新系统四位码、D300 不认」是错的。
  规则仍然是**底子码必须与滑块类型一致**：饱和度/色相为有效值 → 彩色底子；为 `FF FF` → `0x064D`。
  ⚠️ 但**换底子拿不到任何东西**：四个底子的定义块是 856 字节定长记录，`STANDARD` 与 `NEUTRAL`
  逐字节只差 36 字节（名字、缩写、档位表、默认滑块），其余 820 字节完全相同 ——
  它们共用同一套色彩处理，差异只在默认参数，而默认参数会被我们写的滑块覆盖。
  详见 `d300/docs/10-firmware-bases.md`。
- **补上「曲线头 8 字节」**：35 个不同曲线的文件头部完全相同，是固定标识而非校验和；AriaID `49 30` 不是问题
- **发现工坊引擎的曲线前变换 H**：`输出 = C(H(x))`，中间调 −18、两端归零。用恒等/反相两个探针测定，用双色阶跃独立验证（白像素实测 18.34%，模型 18.14%，不做处理 23.65%）
- **★ 曲线能不能执行，看八个滑块的第 2、3 字节**：638 字节文件必须写 `01 01`，写 `80 80` 时那 578 字节曲线块被**静默丢弃**。
  原厂 116 个文件无一例外（52B 全 `80 80`，638B 全 `01 01`）。这是真机上折腾三轮才逼出来的
- **★ 机身也做同一个 H**：硬阶跃 50% 交点落在输入 144.6（模型 `H⁻¹(128)=146.1`），
  从 gamma 曲线反推的机身 H 与工坊 H 相差 **+0.95±1.04 级** → **补偿只需做一份**，卡里出图与工坊出图一致
- 附 **30 个可直接装机的带曲线 NCP**（最终发布版 `d300/ncp/release/`，补偿版；
  未补偿版与验证探针另存），以及完整的判定数据 `d300/docs/07-camera-verification.md`
- **★ 成片差距已量化**：同一张 RAW 导出 30 对同机位样片（滤镜 01–30 全覆盖），逐像素比对 ——
  影调偏差全部 ≤4.2 级、影调曲线 RMS 中位 3.6 级，但整体平均差 8.4 级，**差距几乎全部来自颜色**。
- **★ 第二版把颜色那两个滑块用起来了**：饱和度/色相按 4 张实拍标定图定标（每档彩度 ×1.13、每档色相 3.5°），
  影调按「留出半幅」重拟合。30 支平均差 **7.94 → 6.17 级（−22.3%）**，22 支变好、8 支不变、0 支变差。
  产物归档在 `d300/ncp/release_v2/`，可逐支对拷比较。
  最干净的例证是 `DREAM`：影调 RMS 仅 2.2 级、ΔL +0.7，却因一层暖调色罩（R−B 差 −26）落到 9.8 级。
  数据、并排图与逐支归因在 [`d300/samples/`](d300/samples/README.md)（第 13 节）
- **★ 第三版修正了「该不该动一支」的判据**：第二版用「上半幅拟合、下半幅打分」，这个切法暗含
  「照片上下两半亮度分布相同」，真实照片不满足。`DEEPTONE_MONOCHROME` 因此被判「不动」，
  可它的 |ΔL\*| 有 4.95（30 支平均 1.43），是全场影调差最大的两支之一。
  换成 2×4 = 8 折交叉验证（7/8 像素拟合、1/8 打分）后，同一支 12.23 → **8.76**。
  30 支平均 **6.17 → 5.98 级**（相对第一版 **−24.7%**），25 支变好、5 支不变、0 支变差；
  8 折留出口径 −23.5%，与整幅只差 1.2 个百分点。
  ⚠️ 口径是 420px 缩略图；第一版那 7.94 来自真实渲染的 30 对成片，第二、三版是在它基础上做的模型外推
  （原分辨率下第一版是 8.41，换算约 ×1.06）。
  见 [`d300/docs/11-kfold-holdout.md`](d300/docs/11-kfold-holdout.md)
- **★ CIELAB 分解把剩下的差距定位到颜色上**：第三版亮度差 |ΔL\*| 平均 **1.36**（彩色组 1.11），
  彩度差 |ΔC\*| **4.09**（彩色组 5.05）—— **影调已基本打平，残差全在颜色**。
  而原版的颜色手法是「按色相区域分别处理」：`MORNING` 在黄区要 +68°、青区要 −51°，符号相反，
  任何单一全局角度只能顾一半。三条出路已逐一排除：换底子（四底子共用一套色彩处理）、
  把曲线当分通道用（`DREAM` 的 LUT 最低输出 46.6，成片通道低到 9.0，不可能是逐通道套用）、
  记录 1 里藏字段（36 字节全部拆开，余下两处 30 个文件完全一致）

### 剩下这些差距还能不能再压

四个实验（`d300/tools/probe_color_ceiling.py`、`probe_int_grid.py`）的结论是：
**参数层面已经到头，卡的是 NCP 这个格式本身。**

- **连续域放开**（饱和/色相允许取任意小数，不受 ±3 档限制）：DREAM 收益 0.01 级、RED 0.04 级、
  STANDARD 0.03 级 —— 这几支的滑块已经踩在理论最优上
- **49 种整数档全穷举 + 2×4 八折留出验证**：彩色 19 支里 16 支已在最优档位；
  剩下 3 支穷举出的「更优档位」在留出集上全部变差（DENIM 全图 −0.25 级、留出 +1.36 级）
  → **真正值得改的 0 支**
- **残差的真实性质是「逐色相各偏各的」**：按色相分 8 扇区、让每区各调各的（机身做不到，只用于测量），
  还能再降 2–3 级（PURE 3.11、MORNING 2.38、DENIM 2.36、TOY 2.06）。
  NCP 只有一个**全局彩度倍率 + 一个全局色相角**，表达不了逐色相映射
- **已排除**：不是柔光/雾化这类邻域运算（细节量比 0.95–1.12，两边相当）

![色彩天花板](d300/charts/color-ceiling.jpg)

实线＝按亮度分 8 段后每段的理论最优彩度倍率（DREAM 从暗部 0.30× 爬到 1.04×，极差 3.47 倍）；
同色虚线＝机身真正允许写进去的那一个固定值。目标要的是一条**曲线**，格式只给一条**水平线**。

### 口径

- 主差距（v1 / v3 两列）用**全图**口径，与 `audit_release.py`、`metrics.csv` 一致
- ΔE00 / 可辨像素 / \|ΔL\*\| / \|ΔC\*\| 用**去剪裁**口径（`diag_residual.py`）——
  高光溢出与暗部截断是机身截断造成的，不是滤镜造成的，混用会得到两套数字
- **v1 那列是真渲染实测**（第一版真在 NX Studio 里渲出图再比）；
  **v3 是按文件里实际存的曲线与滑块外推的预测值**，没有重新渲染。两列同口径可比，但 v3 是估计
- 全部数字在 420px 缩略图口径；原分辨率下第一版是 8.41 级，换算约 ×1.06
- 样片只有一张（DSC_3891），换题材重跑才知道这些数字是否普遍成立

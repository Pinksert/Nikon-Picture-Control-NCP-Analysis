# 第 38 字节：闪退不在底子，在「哪个命名空间」

> 状态（2026-11-02 11:35）：`_probe_batch_fix` 去掉 B8 之后**照样闪退**，
> 事件日志偏移还是 `Rome2.dll +0x13d8f2`，一字不差。
> 于是「只有 BINARY 越界」这个结论被推翻：**只要写 08xx 就崩**。
>
> 顺着这条线查下去，剩下的可疑对象只有一个 —— NCP 记录 1 的**第 26 字节**
> （文件偏移 38，也就是 `<CustomData>` 的第 38 字节）。它只出现 0x00 / 0x02
> 两个值，而反汇编的钳位正好是 `8 / 2 / 1`。已备好 `_probe_kind8` 去验它。

## 一、`_probe_batch_fix` 仍然崩

7 张、去掉 `0x0813`、只留 `0801 / 0808 / 080B`（这三个在 kind=8 组里**都存在**）。
11:10:57 打开 → 退出，日志：

```
错误模块: Rome2.dll  异常代码: 0xc0000005  偏移: 0x000000000013d8f2
```

与 `_probe_batch`（含 B8）**同一偏移、同一签名**。

那么 `docs/18` 第四节那个二选一就有了答案：

| 假设 | 预测 | 实测 |
|---|---|---|
| 命名空间是 8 | B1–B7 能开 | ✗ 崩了 |
| 命名空间是 1 | 08xx 全崩 | ✓ 崩了 |

**结论：我们写出来的 NCP 一律被当成 kind=1。** 创意底子不是「BINARY 一个越界」，
而是**整组都够不着**。官方那 20 支创意滤镜的底子，走 NCP 这条路一个都搬不过来。

## 二、反证：渲染读的是 `<CustomData>`，不是 `<ExportData>`

sidecar 里同一份滤镜写了两处（`sidecar_batch.embed_data`）：

| 位置 | 第 38 字节 | 含义 |
|---|---|---|
| `<ExportData>` | **0x02** | NX Studio 自己写「当前应用态」 |
| `<CustomData>` | **0x00** | 滤镜原始定义（= 磁盘 NCP 原样） |

`_probe_profile` 里 `0x0014 / 0x03D5 / 0x00D6`（D2X 模式 I/II/III）**只在 kind=1 组存在**，
kind=2 组里没有它们。如果渲染读的是 `<ExportData>`（0x02 → kind=2），这三张必崩。
**它们正常渲染了**（读数见 `19-probe-results.md` 第七节）⇒ 渲染走 `<CustomData>`。

这条反证很重要，它把怀疑范围从「两处字节」收到「一处」：
**要改的是 `<CustomData>` 的第 38 字节。**

## 三、593 份现成 NCP 的头部长什么样

```bash
python d300/tools/ncp_header_stats.py --csv d300/samples/ncp_header.csv
```

记录 1 的布局（638 字节的标准形态）：

```
版本 4B("0100") | 名字 20B | 底子 2B | ← 这两个字节 → | 滑块 8B
                                      [26]  [27]
```

全仓库 593 份 NCP（我们生成的 + nikonpc.com 第三方 + 原厂工具出的）统计：

| 底子 | byte26 | 份数 | 出现在哪个 kind 组 |
|---|---|---|---|
| 0001 / 00C3 / 03C2 / 0486 / 04C7 / 064D | 0x00 **或** 0x02 | 452 / 91 | kind 1、2、8 都有 |
| **0014 / 03D5 / 00D6** | **只有 0x00** | 1 + 1 + 1 | **只在 kind=1** |
| **0801 / 0808 / 080B / 0813** | 只有 0x00 | 都是我们自己生成的 | **只在 kind=8（0813 不在任何组）** |

规律很清楚：

- 编号**同时**存在于 kind=1 和 kind=2 的 → 两种写法都能见到（作者按机身代际分别生成）；
- 编号**只**存在于 kind=1 的 → 全部 0x00，一份 0x02 都没有；
- 编号**只**存在于 kind=8 的 → 全世界没有一份第三方 NCP 这么写（因为写不出来）。

第 38 字节的取值只有两个：**0x00（502 份）、0x02（91 份）**。没有 0x08 —— 也没有人写成功过。

另外 52 份是 636 字节的老形态（记录 1 只有 34 字节，没有底子字段，`00 FF` 直接接滑块），
它们把 `0x00FF` 读成「底子」纯属解析错位，不影响上面的结论；`read_ncp()` 应当补一条：
记录 1 长度 < 36 时按「无底子（=STANDARD）」处理。

## 四、反汇编里那三个值

`docs/18` 第二节抄下来的钳位：

```asm
cmp edx, 8      ; ≥8 → 8
cmp edx, 2      ; ≥2 → 2
                ; 否则 → 1
shl edx, 0x10
add edx, ecx    ; key = (kind << 16) | 编号
```

命名空间只可能是 **1 / 2 / 8**，而文件里那个字节只会取 **0x00 / 0x02**。
0x02 正好对上 2，0x00 正好对上 1。**0x08 → 8 是唯一没被否认的格子。**

## 五、第 38 字节到底是什么

三种可能，都能被同一个实验分开：

| 可能 | 预测（写 0x08） |
|---|---|
| A. 就是命名空间 | `0x0801` 查得到 → DREAM 正常渲染，与 STANDARD 明显不同 |
| B. 只是「应用态」标记，命名空间在别处 | 仍然崩，偏移还是 0x13d8f2 |
| C. 是命名空间但加载器只认 0/2 | 不崩、但底子回落成 STANDARD（画面与对照一致） |

实验包：

```bash
python d300/tools/pack_kind_probe.py
# → _probe_kind8/      K0_STD_NS8(0001) + K1_DREAM_NS8(0801) + K2_SEPIA_NS8(080D)，第38字节全 0x08
# → _probe_kind8_b/    只有 K0_STD_NS8（A 包崩了再看这个）
```

三张都是**恒等曲线**，所以画面上出现的任何差别都只来自底子本身。
判读见工具输出最后一段；一句话：**K1/K2 与 K0 明显不同 = A 成立，创意底子解锁。**

`_probe_kind8` 三张打开即崩，事件日志：

模块       Rome2.dll 2.9.1.3000

### 8.1 第五节那三种可能，只有一种活下来

| 可能 | 预测 | 实测 |
|---|---|---|
| A. 第 38 字节就是命名空间 | `0x0801` 查得到，DREAM 正常渲染 | ✗ 崩 |
| B. 只是应用态标记，命名空间在别处 | 仍然崩，偏移 0x13d8f2 | ✓ **正是这条** |
| C. 是命名空间但加载器只认 0/2 | 不崩，但回落成 STANDARD | ✗ 崩 |

### 8.2 反汇编复核（这次把调用链走到底了）

查表函数本体 RVA `0x13A170`：

```asm
0013A170  test edx, edx          ; edx = kind
0013A172  je   0x13a1e8          ; kind==0 或 base==0 → 返回 0
0013A178  cmp  edx, 8
0013A17B  jl   0x13a184
0013A17D  mov  edx, 8            ; ≥8 → 8
0013A184  cmp  edx, 2            ; ≥2 → 2 ；否则 1（cmovge）
0013A19A  shl  edx, 0x10
0013A1A4  add  edx, ecx          ; key = (kind<<16) | base
0013A1B0  cmp  edx, [rax-0x68]   ; 线性扫，每次 4 项（步长 0x1a0 = 4×0x68）
...
0013A1D4  mov  eax, ecx          ; ← 没找到就返回条目计数 38，不是 −1
0013A1D6  ret
```

调用点只有 6 处，离崩溃最近的是 `0x13D8B0`（崩溃点在其后 66 字节）。它前面一行：

```asm
0013A75B  mov  edx, [rbx+0x1b0]  ; kind ← profile 结构里的字段
0013A761  mov  ecx, eax          ; base ← profile 开头的 word
0013A763  call 0x13a170
0013A772  imul rsi, r8, 0x68     ; 拿返回值当索引（38 → 越界）
```

**`kind` 是从 `[profile+0x1b0]` 取的，不是从文件某个字节直接读的。** 它是加载器
在解析时替我们填的字段；把 0x08 写进第 38 字节，进到 `edx` 还是 1，
所以 key 依旧是 `0x00010801` → 查不到 → 返回 38 → `imul` → 空指针 → 崩。

### 8.3 旁证：这个容器从来不承载 kind=8

- 全仓库 **593 份 NCP**（我们的 + nikonpc.com 第三方 + 原厂工具），记录 1 的版本
  字段**清一色 `"0100"`**，没有第二版；
- 第 38 字节只有 **0x00（502 份）/ 0x02（91 份）**，**没有一份 0x08**。

结论不是「我们还没找到写法」，而是：**NCP 这个容器表达不了 kind=8**。
创意底子 `0x0801–0x0814` 只活在 NP3 的原生指针里（NP3 里它就是两字节编号，
由 NP3 自己的加载路径认）。

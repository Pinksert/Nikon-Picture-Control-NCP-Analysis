# 探针读数（2026-11-02）：机内到底还剩没剩

> 一句话：**没剩了**。饱和度字节卡死在 ±3（越界一律压回边界），换底子有力量但方向不对，
> 朝官方 NP3 一步都近不了。`oracle_global.py` 算出的那 0.9 个 ΔE00，机内拿不到。

这一轮本该用 sidecar 批处理跑，实测这条路在 NCP 上不成立（见 `13-sidecar-batch.md` 顶部），
改成「导入 NCP + 手动套用」。8 份探针都是从 `ncp/release/` 的成品上改**一个字节**，
所以和 `samples/real_v3/` 的同槽号成片只差那一个字节，读数没有混杂。

复现：

```bash
python d300/tools/pack_range_probe.py --ncp-only     # → _probe_range/ncp + manual
# NX Studio 导入 8 个 NCP，P1..P8 逐张套用 → 导出 → 放进 _probe_range/manual
python d300/tools/probe_range_read.py --dir "…/_probe_range/manual"
```

| P1 | 7 | 饱和度 −6 | 0.33 | −0.00 | **+0.00%** |
| P2 | 7 | 饱和度 −9 | 0.33 | −0.00 | **−0.01%** |

（Δ 对官方：负值才是「更接近 NP3」。八支里最好的也只是 −0.04，等于没动。）

## 二、负越界：字节被压回 −3

P1（−6）、P2（−9）渲出来和释放版**一模一样**：彩度变化 +0.00% / −0.01%，
两张之间逐像素平均差 **0.19 级**（就是 JPEG 编码噪声）。
SILENCE 释放版的档位本身就是 −3，所以这不是「改了没效果」，是**越界值被截到边界**。

## 三、正越界：同样截在 +3

P3/P4 确实变了，但变的幅度只够 +3 的量。拿 `14-slider-calibration.md` 的每档 ×1.118 复算：

| 探针 | 起点档 | 若按 +6 全吃（档数） | 预测彩度 | 实测 |
|---|---|---|---|---|
| P3 DENIM | 0 | 6 档 → ×1.95 | +95% | **+36%** |
| P3 DENIM | 0 | 截到 +3（3 档）→ ×1.40 | +40% | **+36%** |
| P4 TOY | −2 | 8 档 → ×2.44 | +144% | **+78%** |
| P4 TOY | −2 | 截到 +3（5 档）→ ×1.75 | +75% | **+78%** |

两边只有「截到 +3」这一列对得上（误差 ≤4 个点）。所以 **±3 是硬边界，写 ±6/±9 只等于写 ±3**。

> 这条把 `18-residual-lut.md` 里「DRAMA/SILENCE/BLEACH/MELANCHOLIC 需要 k=0.64、
> 即 −6 档」那条升级路彻底封死了。那 4 支只能靠后期 LUT。

## 四、换底子：有力量，但方向不对

底子字节确实被读（P5–P8 都动了 1.4–2.2 个 ΔE00，与 `14` 测的 2.36 同量级）：
VIVID 能把彩度抬 13–16%，NEUTRAL 能压 5%。**但抬完离官方更远或持平**：
四支的 Δ 是 +0.21 / −0.04 / +0.22 / −0.03。

原因不复杂：官方那 16 支走的是**创意底子（0x0801–0x0814）**，它的色彩变换是逐色相的重排，
不是「整体再浓一点」。基础底子里挑一个最浓的，只能把整幅画一起推，推不出逐色相的形状。

## 五、还剩一条没验的路

创意底子编号 0x08xx 到底认不认 —— 这是唯一还能动的维度，也是官方 16 支真正用的东西。
探针已备好（恒等曲线 + 只换底子编号，8 份）：

```bash
python d300/tools/pack_baseid_probe.py --ncp-only
# NCP → _probe_baseid/ncp（B1 STD … B8 BIN）
# 底片 → _probe_baseid/manual（B1_STANDARD.NEF … B8_BINARY.NEF，导出即 B1_STANDARD.JPG）
# 读：python d300/tools/probe_baseid_read.py --dir "…/_probe_baseid/manual"
```

判据只有一条：B5–B8（08xx）与 B1（0001）渲出来**不一样**，就说明创意底子能写进 NCP；
如果四张 08xx 全都等于 B1，这条路封死，机内就真的到此为止了。

## 六、批量 sidecar 路线恢复（2026-11-02 11:10）

上午那次「8 张全变 SILENCE」的误判已经查清，结论反过来了：**NX Studio 是读 sidecar 里内嵌的 NCP 的。**

- `_probe_flag/` 5 格（原样 / 只改 `rdf:about` / 只改 `Apply*` / 都改 / 照抄 NX 自写版），
  同塞 TOY +6：**五张彩度全是 17.52**，与手工套用的 P4 ΔE00 只有 0.27–0.32（SILENCE 参考是 7.91）。
  也就是说那两处字段根本不是原因，我 11:00 那版推断是错的。
- `_probe_name/` 4 格（内容逐字节相同、只改名字，路径 66 / 75 / 76 / 142 字符）：
  **全部 17.52**。连当初那个带 `+` 号的 `R4_TOY_sat+6` 也正常生效。文件名长度这条排除。
- 真因是**扫描时序**：`_probe_range/` 目录注册 `09:47:26`，8 份 sidecar 落盘 `09:47:25.7–26.1`
  （每份间隔约 50 ms）—— NX Studio 边写边扫，扫到某张 NEF 时它的 sidecar 还没出现，
  就缓存了「无调整」；NEF 是 `copy2` 复制的，mtime 停在 5 月，没有变化能触发重读。

**规则：整包写完，再让 NX Studio 打开目录。** 工具：

```bash
python d300/tools/pack_sidecar_batch.py --ncp-dir ../_probe_baseid/ncp \
                                        --out   ../_probe_baseid/batch
```

它一次写完 8 张 NEF 副本 + 8 份配对 sidecar，并逐份校验（CustomData 比特一致、
Export 第 38 字节 = 0x02、曲线读出是恒等），顺手把 NEF 的 mtime 刷成现在。
这次底子探针就走这条路：打开 `_probe_baseid\batch`（**不要再逐张手动套**），
Ctrl+A 导出到 `d300/samples/probe_baseid`，然后 `python d300/tools/probe_baseid_read.py`。

以后换 NCP 版本要重出 30 支样片，也是同一条命令换个 `--ncp-dir`，不用再手点 30 次。

### ⚠️ 这批 8 张会让 NX Studio 闪退（2026-11-02 11:20 补）

`B8_BINARY` 的底子编号是 `0x0813`，而 NX Studio 的 Picture Control 注册表里
**根本没有 0x0813**（创意底子只登记到 `0x080D=SEPIA`）。查不到 → 返回表长当索引 →
越界取到空指针 → `Rome2.dll` 崩溃。

改用这两个目录：

- `_probe_batch_fix`（7 张，去掉 B8）—— 用来判别 08xx 到底认不认
- `_probe_profile`（7 张，全部是 kind=1 合法编号）—— 扫从没用过的 5 个底子

根因与完整注册表见 [20-ncp-crash-and-profile-table.md](20-ncp-crash-and-profile-table.md)。

### ⚠️ 去掉 B8 也没救（2026-11-02 11:35 补）

`_probe_batch_fix`（7 张，只留 0801/0808/080B）11:10:57 打开，**照样崩**，
偏移还是 `Rome2.dll +0x13d8f2`。所以不是「BINARY 越界」，是**所有 08xx 都够不着**，
我们写出来的 NCP 一律被当成 kind=1。详见
[21-namespace-byte.md](21-namespace-byte.md)，判别包是 `_probe_kind8`。

## 七、底子这一格是活的：kind=1 那 5 个从没用过的底子（2026-11-02 11:10）

`_probe_profile` 7 张全部正常打开、正常导出（没有崩，因为编号都在 kind=1 组里）。
恒等曲线，所以读到的差别全部来自底子本身。共用 `P0_STANDARD` 的中间调遮罩
（147874 像素，基准 C* 均值 12.17 / 中位 6.73 —— 这是一张低饱和的场景）。

**五个全部独立生效**，没有一个回落、没有一个只是换了张皮：

- PORTRAIT 与 STANDARD 差 3.90，与最像的 D2XMODE I 也差 2.58；

也就是说：**底子这一维在 NCP 里是真能调的，过去 26 支全压在 STANDARD 上是浪费。**

但别急着高兴，量级要看清：

| 方向 | 谁能推 | 推多少 |
|---|---|---|
| 更艳 | 只有 **LANDSCAPE** | C* × 1.092（+9.2%） |
| 更淡 | D2XMODE II / I | C* × 0.843 / 0.877（−16% / −12%） |
| 更亮 | PORTRAIT | ΔL* +1.52 |
| 更暗 | D2XMODE III | ΔL* −1.46 |

对照 `14-slider-calibration.md` 与第五节的 P5–P7：**VIVID 能把 C* 抬 13–16%，
当年对 ΔE00 只换来 −0.04 ~ +0.22。** LANDSCAPE 的 +9.2% 比它还小，
方向虽然对（我们系统性的毛病是偏淡，见 `docs/15`），量级却同阶 ⇒ **单独换底子，预期收益很小。**

两点保留：

1. 这张底片 C* 中位只有 6.73，是低饱和场景；LANDSCAPE 的真实作用集中在绿/蓝，
   在饱和场景里幅度会更大。要定量得换一张高饱和底片再跑一遍。
2. 底子改变的是曲线**之前**的输入映射，所以换底子必须重配曲线 —— 不能拿现有 26 条的
   曲线直接套。真要压这 0.9 个 ΔE00，得按底子重跑一遍拟合，那是另一轮工作量。

真的大头还是 `19`：如果 `_probe_kind8` 通了，16 支「创意底·彩色」就能用上
官方那套逐色相重排的底子，而不是靠一条一维曲线硬扛 8.21 级的差距。

### ⚠️ 信息栏里七张都显示 P0_STANDARD（2026-11-02 11:20）

不是没套上，是显示层的问题：sidecar 的 `<PictureControl>` / `<SelectedPictureControl>`
全部沿用模板的 1，NX Studio 拿这个 id 去查内部表，表项 1 = 本次扫描第一份的名字。
像素是按各自文件里的 blob 渲的 —— 七张两两不同，`P6` 单色那张直接变黑白，
名字若真是 P0 它不可能变灰。证据、复现与规则写在
[13-sidecar-batch.md](13-sidecar-batch.md) 第九节，对比图 `charts/profile-bases.jpg`。

### 这一格里「0.9 个 ΔE00」也拿不到（2026-11-02 11:45 结论）

上面说的「按底子重跑一遍拟合」，成本与产出要重新估：三格字节全部实测关闭
（底子只能 kind=1 的 9 个、饱和度硬钳 ±3、第 38 字节写 0x08 必崩），
把 `oracle_global.py` 的区间换成实测可达值重跑，26 支上界 **4.43**，与不计档位的
4.44 只差 0.01。所以这一格不是「还有 0.9 没取」，而是「0.9 里的大半，
是另一次曲线拟合的事，不是换底子的事」。见
[22-in-camera-ceiling-locked.md](22-in-camera-ceiling-locked.md)。

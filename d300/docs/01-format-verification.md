# 尼康优化校准（NCP / NP2 / NP3）—— 独立验证与延伸分析

> 对象：`github.com/Pinksert/Nikon-Picture-Control-NCP-Analysis`（已克隆到 `_ref/NCP-Analysis/`）
> 日期：2026-10-26 ｜ 复算脚本：`_ref/ncp_audit.py`（不引用仓库代码，自行实现解析）
> 与 D300 Controller 项目的关系：App 已有「NCP 滤镜导入」功能，本文档解决它一直没跑通的那一步。

## 摘要

仓库的**核心格式结论全部成立**，我用独立实现复算通过：52 字节布局、8 滑块映射 96/96、NP2/NP3→NCP 端到端 12/12 逐字节一致、638 字节曲线结构。

但它有**四处错**，其中一处直接导致它自己声称的"逐字节一致"用它的脚本复现不出来；另有一处把"猜测"写成了"待确认"。

更重要的是，仓库挂在「未验证」里的那条 —— **机内载入这一步还没跑通** —— 我在 D300 固件里找到了定案的直接证据，并据此定位到 App 现有实现的一个**真实 bug**：

> D300 固件只认 `A:\NIKON\CUSTOMPC\PICCONnn.NCP`；App 现在写到**卡根目录**，机身永远找不到。

## 一、验证通过的部分（独立复算，非引用）

### 1.1 52 字节 NCP 布局

对 `presets/` 里 8 个原厂 NCP（6 个基础 + `M.NCP`/`S.NCP` 两个带曲线样本）逐一解析，6 个 52 字节文件全部符合：

| 字段 | 偏移 | 实测 |
|---|---|---|
| 魔数 | 0..4 | `NCP\0` ✓ 全部 |
| 记录类型 | 4 | `1`（大端 u32，**不左移**）✓ |
| 记录长度 | 8 | `36` ✓ |
| 版本 | 12 | `0100` ✓ |
| 名字 | 16..36 | 20 字节，ASCII，补零 ✓ |
| 底子编号 | 36 | 大端 u16 ✓ |
| 未知 | 39 | `FF` ✓ 全部 |
| 结束标记 | 48..52 | `00 00 00 00` ✓ |

> 顺带确认一个容易写错的地方：NCP 的记录类型是**裸大端 u32**（`00 00 00 01`），而 NP2/NP3 的卡片类型是**类型左移 8 位**（卡 1 = `00 00 01 00`）。两者不是同一套编码，解析函数不能混用。

### 1.2 滑块映射 96/96

我自己实现 `值 = round((b0 − 0x80) × b1 / 16)`，对 6 个预设 × NP2/NP3 = 12 个文件重算 8 个滑块位：

```
滑块字节命中 96 / 96
```

与仓库结论完全一致。

### 1.3 端到端 12/12 逐字节一致

用我自己的合成器重建 52 字节文件，与尼康原版 NCP 比对：

```
STANDARD   .NP2 52/52 一致    STANDARD   .NP3 52/52 一致
NEUTRAL    .NP2 52/52 一致    NEUTRAL    .NP3 52/52 一致
VIVID      .NP2 52/52 一致    VIVID      .NP3 52/52 一致
PORTRAIT   .NP2 52/52 一致    PORTRAIT   .NP3 52/52 一致
LANDSCAPE  .NP2 52/52 一致    LANDSCAPE  .NP3 52/52 一致
MONOCHROME .NP2 52/52 一致    MONOCHROME .NP3 52/52 一致

结论：12/12 组端到端逐字节一致
```

**但前提是我先修掉了仓库的一个 bug**（见 2.1）。用它自带的 `np2ncp.py` 直接跑，结果是 **0/12**。

### 1.4 638 字节曲线结构

`M.NCP` / `S.NCP` 是尼康软件真实导出的带曲线文件，独立解析结果：

| 文件 | 记录链 | 头部 0..7 | 控制点 | LUT |
|---|---|---|---|---|
| `M.NCP` | type=1 len=36 + type=2 len=578 | `49 30 00 FF 00 FF 01 00` | 3 点 `(0,0)(73,140)(255,255)` | 首 0 末 32767 |
| `S.NCP` | 同上 | 同上 | 4 点 `(0,0)(69,175)(179,81)(255,255)` | 首 0 末 32767 |

关键交叉检验 —— **控制点的 (x,y) 与 LUT 在同一 x 处是否吻合**：

| 文件 | 控制点 | 声称值 | LUT 实测 |
|---|---|---|---|
| M.NCP | x=73 → y=140 | 54.9% | 54.7%（17933/32767） |
| S.NCP | x=69 → y=175 | 68.6% | 68.6%（22462/32767） |
| S.NCP | x=179 → y=81 | 31.8% | 31.7%（10374/32767） |

误差 ≤0.2%，**"头部字节 8 是点数、字节 9 起每点 (x,y)"这条完全成立**。

### 1.5 参数范围与枚举 —— 与 D300 说明书逐条对上

从 `D300_NT(Sc)04.pdf`（PDF p177 = 手册 p151）核对：

- 锐利化：`A` 或 `0..9` → 仓库「NCP 最小是 0，钳位」正确
- 对比度：`A` 或 `−3..+3`
- 亮度：`−1..+1` → 仓库「NCP 只有 ±1」正确
- 饱和度 / 色相：`A` 或 `−3..+3`
- 调色枚举：`B&W / Sepia / Cyanotype / Red / Yellow / Green / Blue Green / Blue / Purple Blue / Red Purple` = 0..9 ✓
- 滤镜效果：`关闭 / 黄 / 橙 / 红 / 绿` = 0..4 ✓

另外 D300 固件 `B3000111.bin` 里搜不到 `FLAT`，也搜不到 `0801`–`0814` 段的创意底子 —— 印证了「平面/自动/20 个创意编号在 NCP 里没有对应曲线」不是猜的。

## 二、仓库的四处错误

### 2.1 ★ 卡 0x200「名字」是 ASCII，不是 UTF-16BE —— 它自己的脚本因此输出 `????`

README 三处写「名字，UTF-16BE，20 字节」。实测原始字节：

```
STANDARD.NP2  卡2  raw = 53 54 41 4e 44 41 52 44 00 00 ...
MONOCHROME.NP3 卡2  raw = 4d 4f 4e 4f 43 48 52 4f 4d 45 00 ...
DREAM.NP3     卡2  raw = 44 52 45 41 4d 00 ...
```

`53 54 41 4e...` = `STANDARD` 的 **ASCII 明文**，与 NCP 的 20 字节名字区编码**完全相同**。

后果：`np2ncp.py` 第 59 行 `d.decode('utf-16-be', 'replace')` 把这串 ASCII 当 UTF-16BE 解，得到一堆汉字，再 `.encode('ascii','replace')` 变成问号：

```
生成 : b'????\x00\x00...'      ← 用仓库自带脚本
原版 : b'STANDARD\x00...'
差异字节位置: [16,17,18,19,20,21,22,23]
```

所以 README 那句「6 个预设 × NP2/NP3 = 12 个文件重建后与尼康原版 NCP 逐字节一致（52/52）」**用仓库里发布的脚本复现不出来，跑出来是 0/12**。它当初的验证应该是另一份脚本做的（`tools/` 里那批 `np2ncp_full.py` 之类），但发布版的 `np2ncp.py` 把它改坏了。

改成 `d.decode('ascii','replace')` 后，12/12 立刻成立。

> **对 App 的直接影响**：这种 `????` 名字一旦写进卡，机内列表里显示的就是问号。导入前应该校验名字字段。

### 2.2 卡 0x10100「说明文字」是 UTF-8，不是 UTF-16BE

8 个基础预设的说明卡原始字节 `e8 bf 9b e8 a1 8c e6 a0 87 ...` 按 UTF-8 解出来是通顺中文：

```
STANDARD     进行标准处理，以获得均衡效果。
NEUTRAL      进行最少处理，以获得自然效果。
VIVID        对照片进行增强处理，以获得鲜艳的照片打印效果。
MONOCHROME   将照片转换为单色。
PORTRAIT     用于制作肤色柔和、自然的人像照片。
LANDSCAPE    用于获得生动的自然风景和城市风景照片。
FLAT         保留各种色调范围内的细节，包括从加亮显示到阴影。
AUTO         从"标准"优化校准开始，照相机自动调节色相和色调。
```

按 UTF-16BE 解就是乱码。这 8 条是原厂文案，App 里可以直接拿来当预设说明用。

### 2.3 `TONING_GUESS` 不是解码结论，是凭空指定

README 说「`PINK` 的调色颜色——按 9（红紫）处理，未确认；SEPIA/BLUE/RED 已确认」。实测 4 个调色类预设的**卡 13（调色）**：

| 预设 | 卡12 滤镜 | 卡13 调色 | 卡14 强度 |
|---|---|---|---|
| SEPIA | `80 00`（关） | **`FF 00`（不适用）** | `90 04`（+1.00） |
| BLUE | `80 00` | **`FF 00`** | `90 04` |
| RED | `80 00` | **`FF 00`** | `90 04` |
| PINK | `80 00` | **`FF 00`** | `90 04` |
| BINARY / CARBON / CHARCOAL / GRAPHITE / MONOCHROME | `80 00` | `80 00`（=B&W） | `FF 04` |

**这四个文件的调色字段是「不适用」，里面根本没有枚举值可读。** 它们的色调烘在底子曲线 `080D`–`0810` 里，而那条曲线在固件里，导不出来。

所以 `TONING_GUESS = {SEPIA:1, BLUE:7, RED:3, PINK:9}` 不是"猜测待验证"，而是**按预设名字人为指定的**（挑的是 D300 调色表里同名的项）。这个工程选择本身合理 —— 但文档的措辞会让人以为"再多测几个样本就能确认"，而实际上这件事**永远确认不了**，因为源文件里没有这个信息。

### 2.4 「LUT 必须单调」不是格式要求

README 第五节写「输出是 15 位，满量程 32767，**必须单调**」。但原厂 `S.NCP` 的 LUT 实测就是**升 → 降 → 升**（对应它 4 个控制点 `(0,0)(69,175)(179,81)(255,255)`），`单调不减 = False`。

说"必须单调"是给自己的工具设的约束，不是尼康的格式约束。**做工具时不必强制单调**，尼康自己的编辑器就允许画波浪。

### 2.5 附带：样本数

README 说 42 个样本（6 NCP + 8 NP2 + 28 NP3）。`presets/` 实际 44 个文件 —— 它没把 `M.NCP`、`S.NCP` 这两个 638 字节曲线样本算进去。小问题，只影响可复现性描述。

## 三、新发现（仓库未解决/未做到的）

### 3.1 ★★★ 卡上真实路径定案：`A:\NIKON\CUSTOMPC\PICCONnn.NCP`

仓库把这条挂在「未验证」，说明书只说了"插槽 1 到 99"（PDF p186），**没写路径也没写文件名**。答案在固件里。

`_ref/D300-firmware-analysis-main/B3000111.bin`（7.0 MB，固件 B 部分）中：

```
0x1A1BEC  'A:\NIKON\CUSTOMPC\PICCON%02d.NCP'     ← 出现 6 次
0x1A1C74  'A:\NIKON\CUSTOMPC\'                  ← 目录
0x1A1C9C  'A:\NIKON\'
0x1A1C10  'A:\NIKON\%s'
0x1A1D2C  'A:\NIKON\CUSTOMPC\%s%02d.NCP'         ← 带前缀的变体
0x1A1CEC  'PICCON'   0x1A1CF4  'NCP'   0x1A1D4C  'MONOCHROME'
```

把固件里**全部** `X:\` 路径串拉出来对照，关于 NCP 的只有 `A:\NIKON\CUSTOMPC\` 这一族：

```
A:\DCIM\  A:\DCIM\100ND300\  A:\MISC\  A:\MISC\AUTPRINT.MRK
A:\NIKON\CUSTOMPC\PICCON%02d.NCP
```

**没有**根目录级的 `A:\PICCON...`，也**没有**全卡扫描的痕迹。这意味着：

> 机身读取卡上个人设定优化校准的唯一途径，就是按 `A:\NIKON\CUSTOMPC\PICCONnn.NCP` 取文件（nn = 01…99）。放到别处 = 机身看不见。

`%02d` 两位补零、上限 99，与说明书"插槽 1–99"完全吻合。仓库在这一点上判断正确。

### 3.2 曲线头部 8 字节：是固定标识，不是校验和

仓库为 `49 30 00 FF 00 FF 01 00` 试了 XMODEM / CCITT / MODBUS / Kermit 四种 CRC16，全不匹配，列为未解决。

我的判断是**方向错了**：把 `presets/` 的 2 个原厂曲线样本 + `output/curve_all/` 里 31 个带曲线的 + `output/` 下 2 个 PORTRAIT 修订版，**共 35 个 638 字节文件**的头部 0..7 全拉出来统计（`curve_all/` 另有 4 个 52 字节的饱和度/色相标定文件，不含曲线，不计入）：

```
49 30 00 ff 00 ff 01 00   →  35 个文件，全部相同
```

而这 35 个文件的控制点数从 3 点到 20 点不等，曲线形状（升/降/波浪）差别极大。

**头部与曲线内容无关 → 它不可能是曲线数据的校验和。** 它是格式标识/版本头（`49 30` 恰好是 ASCII 的 `I0`）。所以：
- 生成文件时原样照抄这 8 字节即可，不需要计算任何东西；
- 这个"未解决问题"可以从清单里划掉。

### 3.3 NP2 / NP3 的卡片集合边界

| 格式 | 卡片 | 说明文字 |
|---|---|---|
| NP2（0210） | 1–18 | 8 个基础预设带，创意预设不带 |
| NP3（0300） | 1–22 | 同上 |

即 NP3 比 NP2 多出**卡 19–22** 这四张，与仓库"0x1300–0x1600 NP3 独有"一致。

### 3.4 卡 19–22 的语义收窄

仓库对四张卡的语义只有问号。把 28 个 NP3 的取值全部摊开，能收窄一部分：

| 卡 | 取值分布 | 推断 |
|---|---|---|
| 21 | 20 个创意预设 = `8A 0A`(16个) / `85 0A`(4个=SEPIA/BLUE/RED/PINK)；**8 个基础预设全部 `FF 0A`（不适用）** | 「**效果级别**」—— 只有创意优化校准才有这个参数，基础预设全不适用，这条特征非常明确 |
| 22 | `88 04`(+2, 18次) / `84 04`(+1, 6) / `80 04`(0, 2) / `7C 04`(−1, 1)，0.25 档步进 | 「**中等锐化**」—— 量程方向与 0.25 档步进都吻合 |
| 19 | 27 个 `FF 01`，仅 `AUTO.NP3` = `80 01`(0) | 无法判定（只有 1 个非空样本） |
| 20 | 28 个全是 `80 01`(0) | 无法判定（恒为 0，无信息量） |

另外确认：**卡 21 的步进码是 `0x0A` 而不是 `0x04`**，套常规公式 `(b0−0x80)×b1/16` 得 `+6.25` / `+3.125`，量纲明显不对 —— 与仓库"该公式对它们不适用"的结论一致，但"仅创意预设有效"这条把语义锁到了「效果级别」。

### 3.5 卡 4 / 5 确认恒定

- 卡 4 = `00 00`，36 个文件全部相同
- 卡 5 = `FF 01`，36 个文件全部相同

## 四、对 D300 Controller 的直接影响

### 4.1 ★ 定位到一个真实 bug：写错目录，所以机内载入永远失败

App 现在的实现（`PtpUsbConnection.sendFileToStorage`，`parentObject` 默认 `0`）：

```kotlin
val handle = ptpConnection?.sendFileToStorage(fileName, bytes, storage) ?: -1
```

`parentObject = 0` = **卡根目录**。而固件只找 `A:\NIKON\CUSTOMPC\PICCONnn.NCP`。

这正好解释了一个一直存在的现象：文件"写入成功"（机身确实返回了对象句柄，日志也打了"已写入存储卡"），但进机身「管理优化校准 → 载入/保存 → 复制到相机」时，**插槽列表是空的**。

代码注释里写的"把文件写进卡根目录"和"不需要任何私有命令"—— 后半句对（确实只用 0x100C/0x100D），前半句错在目录层级。

### 4.2 修法

三个层次，从稳到激进：

1. **先解析后写入（最小改动）**
   遍历 `storage → NIKON → CUSTOMPC` 拿到父句柄，再 `sendFileToStorage(..., parentObject = custoPcHandle)`。`readNcpSlots()` 同样改成在 `CUSTOMPC` 里列举，而不是根目录。
   前提：卡上已经存在这个目录 —— 只要用户曾经在机身上「复制到存储卡」过一次，目录就在。

2. **目录不存在时自动创建**
   PTP 标准的做法是 `SendObjectInfo` 带 `ObjectFormatCode = 0x3001`（Association / 目录）创建目录，先建 `NIKON` 再建 `CUSTOMPC`。**这一步需要真机验证 D300 是否接受** —— 建议先做探测：`supportsOperation(0x100C)` 有了，但创建目录是否被允许得实测。

3. **兜底兜底**
   建目录失败时不报"写入失败"，而是明确告诉用户："请先在机身上执行一次 管理优化校准 → 载入/保存 → 复制到存储卡，把目录建出来，再回来导入。"

### 4.3 顺带该补的两件事

- **名字字段校验**：导入前检查 NCP 第 16–35 字节是否为可打印 ASCII。若全是 `?`（正是仓库那个 bug 的产物），提示"这个文件的名字是乱码，机内会显示问号"。
- **插槽号与实际文件对应**：固件还有一条 `A:\NIKON\CUSTOMPC\%s%02d.NCP`（带 `%s` 前缀），且 `MONOCHROME` 字符串紧挨着它 —— 说明机身自己保存时文件名可能不是 `PICCONnn`。读插槽列表时别只匹配 `PICCON(\d{2})\.NCP`，建议放宽到 `*.NCP` 再按名字解析，否则会漏掉机身自己存的文件。

### 4.4 还能做什么（可选，价值递减）

- 用 3.2 的结论简化生成器：曲线头 8 字节直接写死，不必迭代求校验。
- 用 2.2 的 8 条原厂说明文案做 App 内的预设介绍。
- 仓库 `output/curve_all/` 里有 31 个已生成的曲线版 NCP（另有 4 个 52 字节的饱和度/色相标定件），其中黑白类/调色类（木炭、石墨、双色、黑碳、单色、棕褐、蓝、红、粉）按仓库自述是"接近可用"的。这些**可以直接拿进 App 做内置滤镜库**，不需要用户自己准备文件。

## 五、仍未解决

|---|---|
| 尼康控制点之间的确切样条算法 | 不需要解 —— 取满 20 点密集采样后插值误差可忽略（仓库已验证到 0.6–14.6 / 32767） |

## 六、和仓库的分歧汇总

| # | 仓库说法 | 实测 |
|---|---|---|

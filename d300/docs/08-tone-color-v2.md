# 第二版：把「饱和度 / 色相」两个滑块真正用起来

> **状态**：本文记录的是第二版，产物归档在 `ncp/release_v2/`。
> 当前发布版是第三版（`ncp/release/`，30 支平均 **5.98 级**），与本文的唯一差别是
> 「留出验证」的切法从上下半幅换成了 8 折，见 [`11-kfold-holdout.md`](11-kfold-holdout.md)。

第一版（`ncp/release_v1/`）只做了影调：八个滑块里对比度、亮度交给曲线，**饱和度与色相一律写
`0x80`（数值 0）**，等于没动。30 对成片说明，彩色那几支的差距主要就落在这两位上
（彩度比 0.71–4.35×、偏色 −26…+32），所以第二版的核心工作是把它们标定出来、用起来。

本文记录这一版做了什么、怎么避免自欺、以及剩下那部分为什么仍然做不到。

---

## 一、三件事

| # | 改了什么 | 依据 |
|---|---|---|
| 1 | **饱和度 / 色相滑块开始写真实值**（−3…+3） | 4 张实拍标定图给出每档倍率与每档色相角 |
| 2 | **影调曲线按「留出半幅」重新拟合** | 整幅拟合会吃掉照片上下半幅的亮度分布差，留出验证能把它挡掉 |
| 3 | **曲线端点按有效样本斜率外推** | 首/末几档像素不足时不参与拟合，`np.interp` 会整段平推，暗部因此被抬高 3–6 级 |

产物：`ncp/release/NIKON/CUSTOMPC/PICCON01–30`（30 个，638 字节）。
第一版原样归档在 `ncp/release_v1/`，可以逐支对照。

## 二、标定：两个滑块到底值多少

用 4 张实拍标定图（同一机位、同一 RAW，只改一个滑块）：

| 对比 | 档数 | 彩度倍率 | 色相 |
|---|---|---|---|
| `SAT-1` → `SAT+1` | 2 | 1.1351 / 档 | — |
| `SAT-1` → `SD`（滑块 0） | 1 | 1.1274 / 档 | — |
| `HUE-1` → `HUE+1` | 2 | — | +3.50 度 / 档 |

取 **每档彩度 ×1.13、每档色相 3.5°**。符号已核对：`-1` 档是**变淡**（×0.885），不是变浓 ——
第一版曾按「-1 会变浓」的简化模型调过一次，方向和实测相反，已作废。

> 这一步是整个第二版的地基。滑块方向搞反，后面所有优化都会往错的方向走。

---

## 三、模型：怎么预测「改完会变成什么样」

机身输出 `O` 由两层构成：曲线给出的亮度、以及彩度/色相给出的颜色偏移。所以对同一个输入：

```
L_new = f(L_O)                      f = 输出域的影调修正（相对第一版曲线）
彩度_new = 彩度_O × 1.13^n          n = 饱和度滑块（−3…+3）
色相_new = 色相_O + 3.5°×m          m = 色相滑块（−3…+3）
```

不必重新渲染：只要有成片对（同一 RAW 的两套导出），就能反解出 `f`、枚举 `(n, m)` 打分。

两条实现上的约束：

- **曲线定义在「机身直出亮度」上**，不能拿它当 `f` 直接套第二次。落地时写成
  `C = T_new∘H⁻¹`，其中 `T_new = f∘T_old`，`H` 是引擎在曲线前插入的那层固定变换（见 `tools/compensate.py`）。
  这里曾经套错过一次，表现为整组文件色块化。
- 彩色预设的影调只在**近中性像素**上拟合。全幅拟合会把色罩当成影调偏差吃进曲线，`MORNING` 实测会从
  11.8 反而涨到 12.5。

## 四、怎么避免自欺：两阶段选参

第一版的评估有个隐藏口径错误：基准用**整幅**误差、候选只用**下半幅**误差，导致「维持原样」被系统性低估，
好几支明明能改的都被判成不动。修掉之后暴露出第二个问题 —— **整幅拟合会过拟合**：

| 槽 | 滤镜 | 整幅拟合 | 留出半幅验证 |
|---|---|---|---|
| 23 | DEEPTONE_MONOCHROME | 12.23 → **8.77** | 13.02 → 13.02（**收益归零**） |

> ⚠️ **这一条后来被推翻了，见 [`11-kfold-holdout.md`](11-kfold-holdout.md)。**
> 「收益归零」是**上下半幅**这个切法造成的假象，不是过拟合的证据：这张图上下两半的亮度分布
> 不是同一套，下半幅那些亮度值在上半幅里没出现过，曲线在那一段没被任何样本约束过，打分当然没收益。
> 换成 8 折交叉验证（7/8 像素拟合、1/8 打分）后，同一支的平均留出收益是 **−2.68 级**，
> 第三版据此改为动它，实测 12.23 → **8.76**。
> 所以下面这套「两阶段」的思路仍然成立（先选结构、再全幅落地），但**用来选结构的那把尺子换了**：
> 不再是单次 50/50 的上下半幅，而是 2×4 = 8 折。原文保留，作为这一版当时依据的记录。

1. **`explore()`**：只用上半幅拟合、只看下半幅打分，挑「在没见过的像素上也能复现」的结构
   （改不改曲线、饱和度几档、色相几档、调色强度几档）。留出半幅上收益 < 0.25 级就不动。
2. **`optimize_slot()`**：结构定了之后，用全幅重拟合曲线（选参数用 CV、落地用全量），写文件。

## 五、结果

全部 30 支，口径 = 三通道逐像素绝对差均值（0–255 级），全部由 `tools/audit_release.py`
**从文件本身重算**（不是优化脚本的自报数）：

| 分组 | 数量 | 第一版 | 第二版 |
|---|---|---|---|
| 单色 17–20 | 4 | 3.92 | **2.77** |
| 新系统 21–30 | 10 | 5.06 | **4.28** |
| 彩色创意 01–12 | 12 | 9.52 | **8.20** |
| 调色 13–16 | 4 | 14.38 | **8.19** |
| **全部** | **30** | **7.94** | **6.17（−22.3%）** |

**22 支变好、8 支不变、0 支变差**；结构自检 30/30 通过。

留出半幅（拟合时完全没碰过的那一半）：**9.08 → 7.08（−22.0%）** ——
与整幅口径几乎一致，说明这 22.3% 不是拟合出来的。

变化最大的几支：

| 槽 | 滤镜 | 第一版 | 第二版 | 做法 |
|---|---|---|---|---|
| 14 | BLUE 蓝色 | 16.00 | **6.88** | 调色强度 0x84 → 0x81，曲线重拟合 |
| 13 | SEPIA 棕褐色 | 13.04 | **7.14** | 调色强度 0x84 → 0x81 |
| 16 | PINK 粉色 | 12.68 | **7.36** | 调色强度 0x84 → 0x82 |
| 7 | SILENCE 静寂 | 10.38 | **6.41** | 饱和度 −3、色相 −2 |
| 15 | RED 红色 | 15.82 | **11.37** | 调色强度 0x84 → 0x82 |

13–16 那四支的根因是**路线错**，不是参数没调好：第一版把它们做成「真单色 + 浓调色（0x84）」＝纯双色调，
原版是「低饱和、仍留部分色彩 + 轻调色」。把调色强度退到 0x81–0x82 之后，四支平均从 14.4 降到 8.2。

## 六、顺手查出来的两个坑

### 1. 端点外推（要如实说清它治好了什么、没治好什么）

`fit_map()` 只统计像素数 ≥250 的亮度档，最暗/最亮那几档常常不达标、直接不参与拟合，`np.interp`
就按两端最后一个有效值平推。现在改成按首/末两个有效档的斜率外推到 `x=0` 与 `x=255`。

**实际效果**：主要改的是**暗部端点**，几支的黑场从 3–6 级降到 1–2 级
（POP 6.0→2.0、TOY 6.0→1.3、DRAMA 3.5→1.5），30 支整体误差多降约 1 个百分点。

**它治不好的**：DRAMA 顶部那段 65 个点的平段。量化过 —— 第一版同一支也有 57 个点，
说明那不是插值伪影，而是**参考图自己就过曝**（`samples/workshop/06_DRAMA.jpg` 亮度 p90 = 251、
p95 = 254，15.7% 的像素在 190 以上）。原版 DRAMA 的高光就是这么硬，曲线照着还原是对的。

同理 BINARY 的 118 点平段是「双色」这个预设的定义本身（阶跃），不是缺陷。

### 2. 底子码的旧结论互相打脸（结论没变，但要说清依据强度）

`docs/05-usage.md` §6.5 写「底子只能用 1/2/3/4」，`docs/07-camera-verification.md` 第 63 行写「`0x0004`
在列表里根本不出现，必须写 `0x064D`」，而 `docs/06-card-pack.md` 那一轮的计划表又写「改成 `0x0004`」——
三处互相打架。

现行的做法是**跟着实拍跑通的那个走**：`0x064D`。理由是它出现在 29 张实拍的那一轮里（此时八个滑块已经是
`01 01`），而 `0x0004` 的所有负面记录都发生在滑块哨兵还是 `80 80` 的轮次 —— 那种情况下 578 字节曲线块
被机身静默丢弃，文件表现会异常，**不能干净地把原因归到「底子码」这一项上**。

所以这里不下「`0x0004` 一定不行」的结论，只说：**它还没有一次单变量的干净复测**（同样的滑块、只换底子码）。
发布包用 `0x064D`，因为它是被实拍验证过的那一个。

顺带把 `verify_one()` 补上 `0x064D`：它原先只认 1/2/3/4，会对 11 个**正确**的单色文件报错 —— 检查器过期，
不是文件错。

## 七、还是做不到的部分

饱和度、色相都是**全局**的：一个倍率、一个角度，作用在画面里所有颜色上。而新系统的招牌手法是
**按色相区域分别处理**。把残差按色相区域分解，最能说明问题（DREAM，第一版数据）：

| 色相区域 | 残差 | 该区域的色相偏移 |
|---|---|---|
| 红 | −10.53 | |
| 橙 | −9.98 | |
| 黄 | −0.18 | |
| 绿 | **+10.90** | **−15.7°** |

同一个画面里，红橙要压、绿要提，方向相反 —— 任何单一倍率都无法同时满足，这就是残差停在 10 级上下的原因。
要再往下走，需要的是分色相饱和度矩阵，或者分通道曲线（R/G/B 各一条 LUT），D300 的自定义曲线两样都没有。

另有两个具体的天花板：

- **有 7 支把饱和度压到 −3 档（硬件下限）仍不够**（DRAMA / SILENCE / BLEACH / MELANCHOLIC / PURE / FLAT /
  FLEXIBLE_COLOR）。原版压饱和的幅度超过 D300 滑块能给的极限。
- **色罩做不出来**。`PURE` +32、`DENIM` +31、`MORNING` +27 这类整体压向青灰的手法，需要分通道曲线；
  `DENIM` 这一支第二版只从 13.24 挪到 13.17，就是因为它的问题几乎全是色罩。

## 八、复现

```bash
cd d300

python tools/optimize_v2.py --dry     # 只评估：看每支的留出验证与建议动作
python tools/optimize_v2.py           # 重算并覆盖生成 ncp/release/（30 个）
python tools/audit_release.py --v1    # 独立体检：不拟合，直接按文件里存的曲线+滑块重算
```

`audit_release.py` 会顺手写出 `samples/metrics.csv` —— 这是 README 里所有数字的唯一来源，
全部由文件本身反算，优化脚本说了不算。

依赖：`numpy`、`Pillow`；样片在 `samples/workshop/`（工坊原版）与 `samples/d300ncp/`（第一版 NCP 出图）。
